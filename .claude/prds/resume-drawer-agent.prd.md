# 이력서랍 — 메신저 회고 에이전트

> 오늘 한 일, 서랍에 넣어두세요. 이력서는 이력서랍이 꺼내드릴게요.

## Problem
프로젝트 단위로 일하는 경력직 개발자는 평소 경력을 기록하지 않다가, 채용공고가 뜨면 기억에 의존해 이력서를 최신화한다. 이때 작업을 통째로 빠뜨리고, 기억이 나더라도 **왜·어떻게** 했는지가 남아 있지 않아 성과를 제대로 쓰지 못한다. 방치하면 이력서 한 번에 주말 이틀을 쓰고도 경력을 증명할 재료를 잃는다.

## Evidence
- 본인 경험: 기록은 사실상 0회. 공고가 뜨면 마지막 이력서를 열고 기억을 더듬어 최신화하는 데 주말 이틀이 든다.
- 본인 경험: 퇴근 후 녹초가 되어 기록에 쓸 수 있는 시간은 최대 10분. 노션·리멤버는 빈 칸을 먼저 채워야 해서 엄두가 안 나 방치된다.
- 본인 경험: 가장 어려운 건 문장 다듬기가 아니라 **기억을 더듬는 단계**, 특히 "왜 그렇게 했는지"의 복원이다.
- 본인 경험: 기록이 쌓여도 공고 요건(예: "대용량 트래픽 처리")에 맞는 경험을 **다시 찾기 어려우면** 결국 기억에 의존하게 된다. 이력서 쓸 때 꺼내 볼 수 있는 정리된 보관함이 필요하다.
- 포럼 피드백: "이력서 쓸 때마다 미리 쓸걸 하며 후회했던 1인" — 같은 문제를 겪는 사용자 1명 확인.
- 다른 직장인도 돈을 낼 만큼 겪는지: Assumption — needs validation via 텔레그램 MVP 사용자 인터뷰

## Users
- **Primary**: 경력직 이직을 준비하는, 프로젝트 단위로 일하는 개발자(1차 사용자: 본인). 퇴근 후 쓸 수 있는 시간은 최대 10분이고, 공고가 떠야 이력서를 연다. 기록은 휴대폰(텔레그램)으로 하고, 이력서는 PC에서 쓴다.
- **Not for**: 이미 꾸준히 기록하는 사람, 이력서 문장 첨삭만 원하는 사람, JD 분석·커리어 로드맵을 원하는 사람(별도 기획과 겹침)

## Hypothesis
We believe **에이전트가 정해진 시간에 메신저로 먼저 오늘 한 일을 묻고, 프로젝트가 끝났다고 알려 주면 쌓인 기록을 STAR로 정리해 주는 것**이 **기억이 사라져 이력서를 제대로 못 쓰는 문제**를 해결할 것이다. 대상은 **퇴근 후 시간이 없는 프로젝트형 경력직 개발자(1차: 본인)**다.
We'll know we're right when **프로젝트 종료 시 생성된 STAR의 80% 이상이 수정 없이 저장되고, 다음 이직 때 이력서 작성이 2시간 안에 끝날 때**.

## Scope
**MVP** — 정해진 시간에 메신저로 먼저 묻고 → 답을 일일 로그로 저장(기밀 일반화 확인 후) → **웹 책장에서 프로젝트를 책처럼 꺼내 읽고 검색** → 사용자가 "프로젝트 끝"을 알리면 그 프로젝트의 로그를 모아 STAR 생성 → 빈칸 표시·근거 로그와 함께 보여 주고 확인 후 저장.

**웹 책장 (기록을 찾는 화면)**
- **책 = 프로젝트.** 책 제목은 프로젝트 이름, 책 내용은 그 프로젝트의 일일 로그를 날짜순으로 엮은 것이다. M3 이후에는 STAR 정리본이 책의 요약 페이지가 된다.
- **책장 칸 = 분류.** 회사로 한정하지 않는다. 사용자가 칸을 만들고 이름을 붙이고("A사", "개인 프로젝트") 순서를 바꾼다. 칸마다 인덱스 라벨이 붙는다. 텔레그램으로 만든 새 책은 '새로 꽂힌 책' 칸에 들어가고 웹에서 옮긴다.
- **진열**: 표지가 보이게 진열한다(제목·기간·대표 태그·진행 중/완결). 검색 결과는 기록(페이지) 단위, 책은 월별 목차 + 날짜순 스크롤로 읽는다.
- **찾기**: 키워드 검색(로그 본문·책 제목), 기술·역량 태그 필터, 기간 필터.
- **기기**: PC 우선(이력서를 쓰는 곳). 휴대폰에서는 칸을 접어서 보여 준다.
- 기록 입력은 텔레그램이 기본이다. 웹 책 화면에서도 직접 쓸 수 있다(AI 없이 쓴 그대로 저장, 지난 날짜 허용·미래 날짜 거절, 기밀 제외 안내 표시). 웹은 읽기·찾기·정리(책 이름 바꾸기, 칸 옮기기, 로그 수정·삭제)도 맡는다.

**MVP 조건 (확정된 결정)**
- **알림 시간**: 사용자가 0시~23시 중 1시간 단위로 고른다. 정각마다 그 시간을 고른 사용자에게만 보낸다(하루 24회 실행).
- **먼저 기록한 날**: 사용자가 그날 이미 기록했다면 알림을 건너뛴다.
- **기록 세션**: 정각 알림을 보낼 때, 또는 사용자가 [지금 기록하기]·`/record`를 누를 때만 세션이 열린다. 세션은 저장·취소하거나 **당일 자정(KST)**이 되면 닫힌다. 세션 밖에서 온 메시지에는 AI를 호출하지 않고 저장하지도 않으며, 안내와 [지금 기록하기] 버튼만 보낸다. (일상 대화로 AI 토큰이 새는 것을 막는다)
- **질문 3개(고정 문구, AI 미사용)**: ① 오늘 무엇을 했나요?(필수) ② 그중 직접 맡거나 결정한 건 뭐고, 왜 그렇게 했나요?([건너뛰기]) ③ 결과나 달라진 점은요? 숫자가 있으면 같이([아직 몰라요]). 답이 올 때마다 기밀을 일반화해 회차별로 저장하고(원문 저장 0), 마지막에 하나의 카드로 모아 확인한다. 세 답은 M3 STAR의 T·A·R 재료가 된다.
- **남용 상한**: 하루 세션 1회(알림·/record 합산, 넘으면 웹 '기록 직접 쓰기' 안내), 세션당 AI 호출 5회, 답 1개 300자.
- **STAR 생성 시점**: 매일이 아니라, 사용자가 프로젝트 종료를 알릴 때 한 번.
- **수치를 지어내지 않음**: 원문에 없는 수치는 빈칸으로 표시하고 추정하지 않는다.
- **기밀**: 저장 전에 고객사명·절대 수치를 일반화하고, 사용자 확인 없이는 저장하지 않는다. 대화 원문은 서비스 저장소에 저장하지 않는다.
- **채널**: 텔레그램(사용자가 봇에서 먼저 대화를 시작해야 먼저 메시지를 보낼 수 있음).
- **다중 사용자**: 처음부터 사용자별 기록을 분리한다. 결제는 붙이지 않는다.
- **외부 AI 호출**: OpenAI Responses API를 `store: false`로 호출해 OpenAI 쪽에 애플리케이션 상태(세션)를 남기지 않는다. 남용 모니터링 목적 보관(최대 30일)은 약관에 명시한다. 국외 이전 동의를 가입 시 별도로 받는다.
- **가입**: 웹에서 가입·동의 → 딥링크로 텔레그램 봇 연결. 웹 로그인으로 자기 기록만 본다. 처음 들어온 사용자에게는 책장 위 '시작하기' 카드로 텔레그램 연결과 알림 시간(기본 21시)을 바로 고르게 한다.
- **약관**: 본문·버전은 DB(`consent_terms`)에서 관리한다. 종류별 최신 게시 버전에 동의하지 않았으면 다시 동의받고, 동의 기록은 본문 버전을 가리킨다. 텔레그램 연결은 연결 버튼에서 별도로 동의받는다.
- **프로젝트가 없을 때**: 봇이 프로젝트 이름을 묻고, 다음 메시지 한 줄로 책을 만들어 바로 질문 1로 이어 간다(AI 미사용). 기록을 시작할 때 어느 책에 들어가는지와 바꾸는 방법([프로젝트 변경], `/project`)을 알린다.
- **프로젝트 끝**: 책 화면에서 STAR를 만들면 그 책은 끝난 책(`ended_at`)이 된다. 현재 프로젝트였다면 비워서 봇이 다음 기록 때 새 책을 묻고, 끝난 책은 봇의 프로젝트 목록에서 빠진다.
- **탈퇴·재연결**: 설정에서 탈퇴하면 모든 기록이 지워진다. 연결을 해제했거나 탈퇴한 텔레그램 계정은 KST 자정까지 다른 계정에 연결할 수 없다(탈퇴·재가입으로 일일 AI 한도를 초기화하는 우회 방지).

**Out of scope**
- 이력서 전체 생성, JD 맞춤 수정 — 기록이 쌓인 뒤의 일이고, 별도 기획(JD 로드맵 에이전트)과 겹친다.
- 카카오톡 연동 — 먼저 메시지를 보내려면 비즈니스 인증·유료 알림톡이 필요할 가능성이 크다.
- 모바일 앱 — 텔레그램 MVP로 검증한 뒤 채널만 옮긴다. (웹 책장은 범위 안이다.)
- 결제 — 사용자 반응 확인 후.
- 회사 시스템(Jira, GitLab) 자동 수집 — 집에서 접근 불가, 기밀 위험.
- 커밋 저장소 자동 연동 — 같은 이유. 커밋 메시지 **붙여넣기**만 다음 단계에서 지원.

**검증 방식**: 운영 연결은 2026-11-10에 마쳤다(Supabase 복구, 마이그레이션 9개 적용, Vercel 환경변수, 텔레그램 webhook). 운영에서는 가입·동의·봇 연결까지 확인했고, 나머지는 로컬 Postgres(Supabase `auth` 스텁)와 **데모 모드**(메모리 데이터·가짜 LLM·웹 봇 시뮬레이터)로 검증했다. 데모 모드는 운영 배포에서는 켜지지 않는다.

**마일스톤 밖에서 추가된 것 (2026-11-10)**: 약관 본문 DB 관리, 텔레그램 별도 동의·재연결 제한·회원 탈퇴, 첫 사용자 '시작하기' 카드, 웹 기록 쓰기, DB 마이그레이션을 Drizzle Kit으로 관리(기존 `supabase/migrations/`는 이력으로 보존).

**사용성 점검(2026-11-10, 대화형 체험)**: 실제 화면 문구와 봇 메시지로 처음부터 순서대로 체험했다. AI 일반화 결과만 예시로 대신했다(이 환경에 OpenAI 키 없음).
- **진행한 단계**: ① 첫 화면 → ② 가입·메일 인증·로그인 → ③ 동의 → ④ 빈 책장 → ⑤ 설정·텔레그램 연결 → ⑥ 봇 연결 → ⑦ `/project`로 책 만들기 → ⑧ 정각 알림(질문 1) → ⑨ 질문 1 답("오늘 seo 화면 개발 함") → 질문 2 표시.
- **남은 단계**: 질문 2·3 답(건너뛰기 포함) → 카드 확인·저장 → 책장에서 새 책 확인 → 칸 만들고 옮기기 → 공고 요건으로 검색 → 책 읽기·수정.
- **바로 반영한 것**: 일상 대화도 AI를 부르던 문제 → 기록 세션 + 고정 질문 3개 + 남용 상한. 자정 만료를 `expired` 상태값으로 남김(응답률 지표에서 무응답과 중도 포기를 구분).
- **관찰**: 질문 1의 답이 짧고 넓으면("SEO 화면") 이력서 재료로 약하다. 질문 2(역할·이유)가 이를 보완하는지, 한 질문에 두 가지를 묻는 게 부담인지는 남은 체험에서 확인한다.
